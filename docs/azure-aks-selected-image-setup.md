# Selected AKS Pod image review

This opt-in reads one to four explicitly selected Pod containers by immutable OCI digest. Name `azure.review.aks.selected_pod_image_secret_indicators` with `content_secret_scans: true`, or `azure.review.aks.selected_pod_image_high_vulnerabilities` with `image_vulnerability_scans: true`. Supply `selected_azure_aks_pod_images` rows with the exact `cluster_id`, `namespace`, `pod`, `uid`, `resource_version`, `container_type`, `container_name`, and `image`; the image must be a canonical `registry/repository@sha256:...` reference, and its host must occur in `selected_registry_hosts`. At most four target rows are accepted; the reused registry reader admits at most two explicit private repository credentials.

The Azure connector requires a scoped ARM credential with `Microsoft.ContainerService/managedClusters/read` and subscription read, an explicit `auth.aks_workloads` entry for the selected cluster, a trusted CA, and a separate Kubernetes bearer token. The Kubernetes identity needs `get` for the `kube-system` Namespace and `get` for the exact Pod in its namespace; an Azure ARM Reader role does not grant these Kubernetes API permissions. Do not supply a cluster-admin kubeconfig, discover credentials implicitly, or grant Secret access. The code binds the configured API origin to the ARM `fqdn` or `privateFQDN` and compares ARM `resourceUID`, Kubernetes namespace UID, Pod UID/resourceVersion/container/image, and OCI digest before and after inspection.

The registry may be anonymously readable, or `auth.registry_auth` may carry an explicit read-only basic or bearer credential for the selected host and repository. The Kubernetes token is never used at the registry. For Azure Container Registry, the repository identity needs `AcrPull` in the classic permission mode, or the `Container Registry Repository Reader` content/read data action in ABAC mode; ARM Reader alone does not grant image bytes. Other selected registries need equivalent repository pull access. The reader refuses redirects and nonpublic registry IPs, verifies OCI digest and layer bytes, and sends credentials only to the selected registry origin. Trivy requires the existing fresh offline database and local Trivy executable; an incomplete clean scan is UNKNOWN.

Azure Arc `Microsoft.Kubernetes/connectedClusters` selections yield UNKNOWN in this adapter. The ARM connected-cluster GET does not supply a Kubernetes API origin that this adapter can bind to its resource, so it does not route a token through an arbitrary owner URL or Arc proxy. A denied Pod GET, missing registry pull permission, changed cluster/Pod, partial OCI bytes, or incomplete detectors also yields UNKNOWN unless a fully bound partial scan recorded a typed positive finding. This is one selected image, not proof of all cluster images or what executed historically.

Official sources: [AKS managedClusters GET](https://learn.microsoft.com/en-us/rest/api/aks/managed-clusters/get?view=rest-aks-2024-05-01), [AKS Kubernetes authorization](https://learn.microsoft.com/en-us/azure/aks/concepts-cluster-authorization), [AKS RBAC Reader](https://learn.microsoft.com/en-us/azure/aks/manage-azure-rbac), [ACR ABAC repository permissions](https://learn.microsoft.com/en-us/azure/container-registry/container-registry-rbac-abac-repository-permissions), [Arc connectedClusters GET](https://learn.microsoft.com/en-us/rest/api/hybridkubernetes/connected-cluster/get?view=rest-hybridkubernetes-2026-05-01).
