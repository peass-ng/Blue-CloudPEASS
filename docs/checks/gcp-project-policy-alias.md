# GCP project policy identity and Data Access checks

The Spanner (`gcp_pci_iam_policy_ca1281da7ab2`) and Pub/Sub
(`gcp_pci_iam_policy_9a8ce875703d`) checks assess configured Data Access audit
policy. They do not certify that logs were delivered, retained, or generated by
an application.

## Native evidence

A Cloud Resource Manager policy can use `projects/PROJECT_ID` while Cloud Asset
Inventory reports the same project's numeric resource name. The collector keeps
both observations and their native identities. An internal observation suffix
separates colliding inventory keys; it does not rename the cloud resource.

The alias proof needs a complete project inventory and IAM policy inventory,
with field coverage and independently recorded requests for:

- `GET /v3/projects/PROJECT` on Cloud Resource Manager, binding the selected
  scope to `projectId` and numeric `name`.
- `POST /v3/projects/PROJECT:getIamPolicy`, requesting policy version 3 and
  collecting the full direct policy.
- An unfiltered, fully paginated Cloud Asset Inventory
  `GET /v1/projects/PROJECT:searchAllIamPolicies`.

The project metadata GET is required even when a successful ancestry request is
available. Extra compute or metrics hydration requests do not establish project
identity. When only IAM policies are requested, the supporting identity read
uses CRM directly without compute or monitoring hydration. A denied unrelated
hydrated field does not erase the independently collected identity fields.
Every IAM envelope request reference, including successful empty CAI pages,
must resolve to an authorized matching native read in the request ledger.
Missing, denied, filtered, duplicated, foreign-scope, or inconsistently paged
request evidence blocks the alias proof.

CAI is a projection: an omitted policy field makes no assertion about its
value. An explicitly present empty field is compared with the direct policy.
A contradiction blocks the alias proof. Supported set ordering is compared on
copies; recorded observations retain their original order and content.
Different conditions, principals, policy versions, or etags are not discarded to
make two views match. Unparsed content and ambiguous duplicates remain unknown.

Only the verified CAI project projection is excluded from project-root
ambiguity. Other observations remain visible. A known, readable resource peer
is outside these project-root checks; an uncertain or unsupported hierarchy
candidate cannot be silently excluded.

## Result requirements

| Result | Required evidence |
| --- | --- |
| PASS | Complete root and ancestor policy evidence enables both DATA_READ and DATA_WRITE for the service; approved, scope-bound required-principal input is present; no known or unresolved exemption applies to those principals. |
| FAIL | Complete applicable policy evidence proves a required log type absent or a required principal explicitly exempted. |
| UNKNOWN | Identity, request authority, field coverage, source completeness, hierarchy, approved principal input, or exemption membership cannot be proved; conflicting views also remain unknown. |
| NOT_APPLICABLE | The observation is a verified CAI projection evaluated through its direct root, or a known resource-level policy outside the project-root criterion. |

A native ancestry response must contain the project self entry and any ordered
folder/organization parents. An empty response does not prove a parentless
project. Parent-only compatibility responses can select additional inventory
reads but cannot certify the project's complete ancestry.

Exact repeated direct pages can retain one observation with merged request
references. Conflicting same-view policies retain evidence and make the
inventory incomplete. The direct root and its distinct CAI projection remain
separate observations.

## Directed verification

The native pipeline tests use inert HTTP responses under the production
transport, collector, snapshot construction, and registered evaluators. They do
not call a provider or execute cloud changes. Relevant test modules are:

- `tests/test_peaso_gcp_project_alias.py`
- `tests/test_peaso_gcp_project_alias_authority.py`
- `tests/test_peaso_gcp_project_alias_collector.py`
- `tests/test_peaso_gcp_project_alias_pipeline.py`
- `tests/test_peaso_gcp_project_alias_order_unit.py`
- `tests/test_peaso_gcp_project_alias_order_pipeline.py`
- `tests/test_peaso_gcp_project_alias_ancestor_authority.py`
- `tests/test_peaso_gcp_project_alias_pages.py`

Fixtures with opaque request labels and no native request ledger continue to
return UNKNOWN. Passing fixtures establish the bounded evaluator behavior, not
live account coverage or real log delivery. Unsupported policy regrouping and
unreviewed resource-peer types remain conservative UNKNOWN cases.
