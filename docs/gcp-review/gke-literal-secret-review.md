# Optional read-only GKE workload literal inspection

The pure candidate with explicit `install()` registration `gcp.review.gke_workload.literal_configuration_secret_indicators` uses the existing secrets group and new default-excluded inventory `gke_workload_literal`, dependent on native `gke_cluster` facts. It scans returned ConfigMap text/UTF8 binary data and Pod literal environment values, arguments and commands through shared offline Kingfisher 1.4.0 and TruffleHog 3.92.5. Common fingerprints merge observations across tools, surfaces, namespaces and clusters into one value finding.

The existing [GKE cluster producer](https://docs.cloud.google.com/kubernetes-engine/docs/reference/rest/v1/projects.locations.clusters/list) lists native clusters with unmasked metadata. [Cluster fields](https://docs.cloud.google.com/kubernetes-engine/docs/reference/rest/v1/projects.locations.clusters) include a **short** `name`, `location`, server-defined `selfLink`, IP `endpoint` and base64 public `masterAuth.clusterCaCertificate`. The bridge cross-checks these facts against exact selected cluster/project scopes, complete source envelopes and successful native request receipts. It never substitutes a fabricated full Cluster.name. A source gap was confirmed: generic envelope identity coalescing can hide duplicate/conflicting native cluster rows. A new optional source validator rejects that ambiguity before coalescing; the installed root-owned hook is exercised directly by the focused tests.

Only boolean `content_secret_scans=true`, an explicitly named check binding, exact `selected_gke_clusters` and originally selected project scopes authorize reads. `selected_gke_namespaces` optionally maps every selected cluster to exact namespace names; otherwise bounded native namespace discovery must complete. Wildcards/discovered projects, endpoint/CA/token overrides and missing authority make no Kubernetes calls. Native cluster dependency envelopes and explicit selection metadata must be retained for consumer verification.

[Google authentication guidance](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/api-server-authentication) documents OAuth and the email scope; [authorization guidance](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/access-control) distinguishes resource authorization from cluster metadata access. The bridge reuses existing pasted tokens, valid Google SDK tokens or already-cached unexpired gcloud tokens, without refresh or helpers. Missing scope metadata does not invent a missing-grant status: native 401/403 is UNKNOWN, while a successful pinned list proves only that returned read. A separate exact proposal requests `cloud-platform` plus `userinfo.email` from refreshable SDK credentials only for the named, opted-in explicit GKE plan. Normal credential scopes are unchanged; root owns this change.

A dedicated stdlib HTTPS connection pins public IPv4 port 443 to the proven native endpoint and uses hostname verification, CERT_REQUIRED, TLS 1.2 or newer and an SSL context containing only the parsed native CA. No generic GCP host/cache expansion, redirects, proxies, filesystem kubeconfig or credential helpers are used. The only paths are GET lists of namespaces, or ConfigMaps/Pods in approved namespaces. Secret values, token volumes, logs, exec, attach, portforward, certificate/key requests and mutations are outside the allowlist.

The [ConfigMap schema](https://kubernetes.io/docs/reference/kubernetes-api/core/config-map-v1/) distinguishes text from potentially non-UTF8 binary data and forbids overlapping keys. This implementation accepts strict canonical base64 decoded to UTF8, returning UNKNOWN for unsupported binary content. The [Pod schema](https://kubernetes.io/docs/reference/kubernetes-api/core/pod-v1/) supplies container, init-container and ephemeral-container literal fields. Native secret/config references are kept as references without dereference; image defaults, runtime expansion, volume contents and other spec/status metadata are not inspected. Omitted maps/arrays are empty only on bound full native objects; missing main containers, ambiguous unions and metadata-only representations do not prove absence.

[Native list pagination](https://kubernetes.io/docs/reference/using-api/api-concepts/) must finish with consistent per-list resourceVersion, no repeated cursor/name/UID, and valid namespace/UID/object identity. Limits are three clusters, five namespaces/cluster, 100 resources/project, three pages/list, 25 objects/page, 128 bridge calls/project, 1 MiB HTTP/response, 4 MiB HTTP/project, 64 KiB literal value, 256 KiB scanned/resource and 1 MiB scanned/project. There are at most 20 containers/class and 128 pairs/arguments. Shared call/cancel/deadline budgets apply with a 60-second cooperative bridge deadline, one-second HTTP idle waits and ten-second maximum per-engine scan timeouts. This is not a hard real-time scheduling guarantee.

Identity HTTP encoding and exact bounded Content-Length or successful native chunk framing are required. A real in-memory http.client test verifies that valid native JSON missing its final HTTP chunk becomes UNKNOWN. Raw bodies are inspected transiently before projection; caller authorization, raw literals, snippets, opaque cursors and raw errors do not enter caches, snapshots or evidence. Persistent data contains native workload name/namespace/UID/resourceVersion, cluster authority hashes, safe references, fixed surface locations and redacted detector coverage.

FAIL means a supported likely secret in completely assessed returned literal configuration. PASS means no supported match on those returned supported fields only; it does not assess all workloads, images, history, runtime or managed secret values. Any denied/partial/malformed/ambiguous/bounded-out/tool-failed assessment is UNKNOWN. Empty lists do not invent a passing resource. Private/DNS-only/IPv6 endpoints, untrusted/missing CA, missing/expired tokens and unproven native aliases remain unsupported or UNKNOWN, with no insecure fallback.

Focused proofs cover actual pinned tools, one-value dedup across clusters/namespaces/surfaces, existing-token success and native RBAC denial, zero-call gating, source ambiguity, CA/endpoint pinning, namespace discovery and selections, references without reads, forbidden paths, paging/version continuity, privacy, truncation, budgets and cancellation. Six source-produced ConfigMap/Pod PASS/FAIL/UNKNOWN full item/index cases use actual native GCP production, Kubernetes HTTP mocks, real envelopes, sealed snapshots and engine MemoIndex. Exact results, source hashes, primary-document fetch receipts and known unproved branches are in [the JSON review](gke-literal-secret-review.json) and `/tmp/peasso-gcp-review-20261019/gke-literal-secret-proposals/`.

No live cloud, infrastructure, deployment, build, whole suite or additional agent was used. Root owns shared hooks, registry/public selection, catalog/copy and admission tests. Root hook integration was observed during finalization; the focused suite was rerun successfully on that state, and initial proposal and regenerated native-source baselines are recorded separately. This worker edited no shared source. This is bounded behavior proof, not full semantic certification. Proposed evidence is two direct sentences: “A likely secret was detected in the returned GKE workload configuration. The value is hidden; offline detection did not validate the credential.”

This does not certify arbitrary encodings or unmatched sensitive metadata.
