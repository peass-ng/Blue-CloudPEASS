# Bounded Cloud Logging application-message secret review

The unregistered candidate `gcp.review.logging.application_log_secret_indicators` scans native application `textPayload` and `jsonPayload` through the shared offline Kingfisher 1.4.0 and TruffleHog 3.92.5 adapters. It uses the new precise inventory `log_secret_sample` and the existing secrets finding group. The existing `log_entry` and `project_log_entry` audit metadata paths are unchanged.

Google documents [`entries:list`](https://docs.cloud.google.com/logging/docs/reference/v2/rest/v2/entries/list) as a POST with parent resources, filter, ordering and pagination. An empty page with a continuation token still requires another request; all parameters except the token stay identical. This candidate generates a 15-minute timestamp window ending at collector read time, orders newest first, selects text/json payloads and excludes audit log names. It only authorizes projects explicitly present in `collector.requested_scopes`, independently requiring boolean `content_secret_scans=true` and the engine’s named-check kind binding. Discovery and wildcard scopes confer no content authorization.

[`LogEntry`](https://docs.cloud.google.com/logging/docs/reference/v2/rest/v2/LogEntry) defines mutually exclusive text, JSON and protocol payloads, a required monitored resource and native log name, and optional split-message metadata. This implementation rejects protocol payloads, split messages, malformed/unbound resources, foreign log names and unsafe numeric project aliases. It makes no claim about other native metadata or log history.

The proposed transport hook runs before generic transport cache creation or credential access. It requests identity encoding, accepts only identity response content, and requires exact bounded Content-Length equality or successfully completed Requests chunk framing. Missing/conflicting framing, compressed responses, stream errors and truncated bodies are UNKNOWN even if received bytes form valid JSON. Raw messages are consumed transiently; returned data is built from scratch with only fingerprints, detector identities, fixed content paths, counts and coverage. No response content, native metadata, cursor, caller authentication or untrusted error text enters the transport cache, collection or request receipt.

Limits are three pages, 100 entries, 50 entries/page, 256 KiB HTTP body/page, 64 KiB UTF-8/message, 512 KiB scanned/sample, JSON depth 12 and 2,048 nodes. A 45-second cooperative deadline surrounds streaming and detector calls, HTTP idle waits are at most one second, and per-engine timeouts are at most ten seconds. A continuation token at a limit, cancellation, denied/failed read, malformed input or either detector unavailable yields UNKNOWN, including partially positive samples. Existing shared SDK locking/scheduling is not certified as a hard real-time bound.

FAIL means a supported likely secret was found in a complete bounded sample by the offline detector pair. PASS means neither detector found a supported match in the sampled returned messages; a zero-result sample is explicitly counted and still requires both detectors. Neither result certifies all logs, arbitrary secret patterns or credential usability. Detection never verifies credentials or reads Secret Manager.

Finding ownership is the project and exact generated query/window. Page/message positions are unstable across reruns and do not identify a durable native logName/insertId owner; arbitrary metadata is deliberately discarded. Investigating or remediating an individual log entry requires a separately authorized lookup outside this implementation.

The focused native HTTP-to-real-collector tests exercise actual pinned positive/negative scanning, text/JSON same-value and cross-check deduplication, persistence privacy, strict framing through the real in-memory http.client/urllib3/Requests chunk parser, native omissions, split messages, pagination and limits, cancellation/tool failures, explicit project authorization and consumer proof rejection. Shared detector/dedup test patterns are attributed to `tests/test_gcp_function_secret_review_20261019.py`; new streaming and application payload proofs are directed tests. Exact results, source hashes and fetched primary-document hashes are recorded in [the JSON review](log-secret-review.json) and `/tmp/peasso-gcp-review-20261019/log-secret-proposals/source-bound-receipt.json`.

No shared source, registration, catalog or UI copy was edited. Root-owned exact hook proposals and their source hashes are in `/tmp/peasso-gcp-review-20261019/log-secret-proposals/shared-hooks.patch` and `shared-hooks.json`; root must still admit the callback and verify engine selection/default exclusion. No cloud calls, live IAM behavior, production throughput, regional fanout, split assembly, payload decoding or full semantic certification were performed.

Proposed evidence: “A likely secret was detected in the sampled application log messages. The value is hidden; offline detection did not validate the credential.”
