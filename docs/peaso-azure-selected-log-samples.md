# Optional selected Azure message-sample scanning

These two readers are integrated locally with production collector, validation, registry and UI hooks. Publication of this local work is separate. Standard metadata scans do not read messages. A selected scan requires `content_secret_scans: true`, the exact named check and its exact native selector; category, framework, bulk inventory or an internal kind string cannot authorize message reads.

| Check | Exact selector |
| --- | --- |
| `azure.review.log_analytics.selected_message_sample_secret_indicators` | `selected_azure_log_workspaces`: `[{"resource_id":"<workspace ARM ID>","table":"AppTraces"}]`. The only supported table enum is `AppTraces` or `FunctionAppLogs`, scanning their native `Message` column. |
| `azure.review.application_insights.selected_trace_sample_secret_indicators` | `selected_azure_application_insights`: `[{"resource_id":"<Application Insights component ARM ID>"}]`. The native component `AppId` determines the query route; only `traces.message` is sampled. |

Select at most four workspace/table or component targets total, within explicit subscription scopes. Customer workspace IDs, App IDs, query strings, token audiences, endpoints, time ranges, cross-workspace IDs and API keys are not selector inputs. The readers never enumerate keys or create resources, mutate logs, invoke application code or validate detected credentials.

The sample window is the fixed preceding hour at collection start. Queries request newest messages in timestamp order, with at most 100 returned rows across all selected targets, 2 MiB per HTTP body, 8 MiB total response bytes, 256 KiB message content per target, 12 selected native HTTP calls and a 120-second native read/scanning deadline. The deadline is checked before and after SDK token acquisition; the existing credential SDK controls its own authentication transport timeouts and OAuth retries, so this is not a hard end-to-end authentication timeout. No pagination is followed. This is a finite sample, not all recent rows or retained history; service-side SDK/ingestion sampling may already have removed messages. A clean PASS requires a nonempty coherent sample and both pinned offline detectors completing without a supported hit. Empty, denied, malformed, foreign, unsupported or incomplete negatives remain UNKNOWN.

| Native read | Minimum read permissions and token audience |
| --- | --- |
| Exact subscription GET (`2022-12-01`) | `Microsoft.Resources/subscriptions/read`; `https://management.azure.com/.default`. Native subscription ID, enabled state and Azure tenant must match the explicit scope and authenticated tenant. |
| Exact workspace GET (`2022-10-01`) | `Microsoft.OperationalInsights/workspaces/read` on the selected workspace; ARM audience. Native full resource identity and `properties.customerId` bind the data route. |
| Workspace query POST to `https://api.loganalytics.azure.com/v1/workspaces/{nativeCustomerId}/query` | Workspace/table query authorization: `Microsoft.OperationalInsights/workspaces/query/read` plus the selected legacy table read `.../query/AppTraces/read` or `.../query/FunctionAppLogs/read`, under the workspace's applicable access-control model. Modern granular table/row access uses the workspace `query/read` Action plus `Microsoft.OperationalInsights/workspaces/tables/data/read` DataAction with the intended table/row conditions, as in Log Analytics Data Reader; no row/table restrictions are bypassed. Token resource remains **`https://api.loganalytics.io`**, requested as `https://api.loganalytics.io/.default`. |
| Exact Application Insights component GET (`2015-05-01`) | `Microsoft.Insights/components/read`; ARM audience. Native `properties.AppId`, Azure `TenantId` and provisioned state bind the selected component. Instrumentation keys and connection strings returned in metadata are discarded. |
| Application Insights query POST to `https://api.applicationinsights.io/v1/apps/{nativeAppId}/query` | `Microsoft.Insights/components/query/read` on the selected component; `https://api.applicationinsights.io/.default`. The official query-authentication walkthrough uses Reader, which includes more read permissions than this scan needs. Delegated authentication also needs the applicable API `Data.Read` consent; existing supported service credentials acquire the fixed query audience through the SDK. Workspace-based applications can impose additional native query restrictions; denial stays unresolved without a broader fallback. |

Metadata-only custom read roles do not establish query authorization. Built-in Reader can include query permissions in these resource scopes; it is inaccurate to say Reader is always insufficient. Prefer reviewed narrow query permissions and the existing workspace/table/row access policy. No Contributor, Publisher, ingestion sender, shared-key, API-key, purge, export or write permission is requested or provisioned. An ARM-only token cannot query these data planes. Existing SDK credentials can acquire the required fixed audiences; the existing Log Analytics audience token profile may serve its workspace query, while no new standalone Application Insights bearer-token input is proposed.

Workspace queries contain a fixed selected-subscription filter and project only typed timestamp, message, workspace customer ID and source resource ID. Each row must belong to that native workspace and a source resource within the selected subscription. The table's `TenantId` column means **Log Analytics workspace ID**, not the authenticated Azure tenant; those identities are checked separately. Application Insights queries use only the exact native AppId route, project typed timestamp/message columns and contain no cross-application parameter or query expression. Neither reader follows user KQL, `union`, `workspace()`, `app()`, URL references or additional result tables.

The documented Log Analytics `200` response containing `tables` plus `error.code=PartialError` permits scanning coherent returned rows: a completed detector's bound hit is FAIL with incomplete coverage, while a negative remains UNKNOWN. The Application Insights v1 query contract does not independently establish that partial-success shape here, so any error-bearing response is unresolved and unscanned. Both APIs require exact result-column types and message timestamps inside the captured window. Snapshot time must be coherent with that window; a clean sample is never inferred from old or missing timestamps.

HTTP query bodies bypass generic cached response helpers. Raw rows, message values, native error details and auth headers are not exported or retained in reader caches. Opaque HMAC locations and native resource-to-query binding receipts survive. Matched values feed the existing bounded `configuration_secret_redactions` union; root must merge the sample ledger before the unchanged declaration/five-reader final scrub. Detector subprocesses run offline with the existing bounded cleanup contract.

Unsupported portions include other log tables/columns, exception/custom-property payloads, complete history, cross-subscription source rows in a workspace, cross-application queries, sovereign/custom hosts, data-plane paging and referenced content. This proposal does not scan intended Key Vault or other secret-store payloads, prove ingestion/delivery, or infer which code is deployed. Explicit stored source artifacts remain covered by the separate [Blob/File reader](peaso-azure-selected-storage-secrets.md).
