# Hosted GCP service account onboarding

The hosted GCP connector uses `hacktricks-cspm-sa-acc-third-p@billing-static-info-no-delete.iam.gserviceaccount.com`. Customers grant this identity read access on each project they want scanned. The account's home project, `billing-static-info-no-delete`, is excluded from both explicit scans and project discovery.

Each connector receives a random project label when created. The customer must set that label to `approved` on every project assigned to the connector. An explicit project is checked with Cloud Resource Manager `projects.get` before inventory reads. “Discover all approved customer projects” uses `projects.search` and keeps only active projects bearing this connector's label. This also prevents one customer's connector from scanning another customer's projects merely because the shared identity can access both. Project labels are authorization markers in this workflow: anyone who can edit the project label can authorize that project for a connector whose label they know.

## Customer setup

1. Create a hosted GCP connector with “HackTricks CSPM service account” and save it. Open **Onboarding** to copy its service account email and unique project label.
2. In each customer project, grant the service account `roles/viewer`, `roles/iam.securityReviewer`, `roles/cloudasset.viewer`, and `roles/serviceusage.serviceUsageConsumer`. Add service-specific read roles if the scan reports permission gaps. The grant can be made at the project level; the service account does not need membership in the customer's organization.
3. Set the displayed label key to the displayed value (`approved`) on each project. Give the service account permission to read the project via Cloud Resource Manager; the roles above normally include `resourcemanager.projects.get`.
4. Enter the desired project IDs, or select **Discover all approved customer projects**. Run a scan after IAM and label changes have propagated. A project without both read access and the matching label is excluded.

The connector's proof label is generated by the API and stored with its encrypted authentication settings. Replacing the connector's authentication generates a new label; update the customer project labels before the next scan.

## Production operator setup

Keep the supplied service account JSON outside the repository. Create a dedicated AWS Secrets Manager secret in account `202533532952`, region `us-east-1`, containing the JSON as `SecretString`. For example, use `aws secretsmanager create-secret --name hacktricks-cspm/gcp-platform-sa --secret-string file:///absolute/private/service-account.json` with the dedicated AWS profile. Do not put the JSON or a base64 copy in Terraform variables, source control, a container image, or an application log.

Set Terraform variable `gcp_platform_sa_secret_arn` to that secret's ARN and deploy the API and collector task definitions. Terraform grants only the collector task role `secretsmanager:GetSecretValue`; the API receives only the ARN to advertise the onboarding option. The collector subprocess reads the key at scan time, checks its project ID and email, and uses it only for that scan. The key itself is never stored in a connector record.

Rotate the service account key by updating the secret value, then revoke the old key in Google Cloud. Existing customer grants and project labels continue to apply because the service account email stays the same. Test with a labeled customer project and confirm the home project and an unlabeled accessible project are absent from both scope lists and stored discovery evidence.
