Systemic issues:
- Severity is inconsistent for "deploy/run as any SA the source can actAs on" entries. Compute, Cloud Build and Cloud Functions are critical; Batch, Apigee, Dataplex, Cloud Deploy and the Cloud Tasks setIamPolicy path were high. These are now normalized to critical. Entries limited to BigQuery or to request-level use keep high.
- Required permissions were sometimes put in `conditions` instead of `requires` (Cloud Deploy targets.create/update), or the wrong resource was required (pipeline instead of target).
- Duplicate edges across HackTricks sub-pages: the SSH-metadata page restated setMetadata. Prefer an _excluded "covered by" line over a second entry.
- HackTricks run-as claims that say "no actAs needed" can be outdated against provider enforcement changes (Dataform strict act-as mode, and possibly Cloud Build's default identity). Verify these against Google docs.
- Consistency check: all files validate. The only load_catalog error is outside scope (aws/cloudfront.yaml wildcard action).

Systemic issues:
- In-place updates of resources carrying UAMIs (ACI full PUT, deployment scripts) can trigger an ARM linked-access check that requires assign/action even though the identity is already attached. The entries only express this as a condition.
